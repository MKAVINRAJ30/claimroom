# ⚡ ClaimRoom

> **A real-time "first to claim" live sales room for small sellers.**  
> Built for **Build Something Real: The Serverpod Hackathon** using Serverpod 4, PostgreSQL, and Flutter.

---

## 🌐 Live Test Link

**Open in any browser (phone or desktop):** https://claimroom.serverpod.space

API server: https://claimroom.api.serverpod.space

Hosted on Serverpod Cloud. No sign-up needed: create a room as a seller, then open the join link on a second device as a buyer.

---

## 🎯 The Problem

Small independent sellers in India and worldwide sell through **Instagram Lives** and **WhatsApp groups**. During live drop sales:
- Buyers comment `"mine"`, `"sold"`, or `"claim"`.
- The seller tries to track claims manually on paper or in spreadsheets while livestreaming.
- **Race conditions**: Multiple buyers claim the same unique item at the same time, leading to double-sales, lost orders, and angry buyer DMs.
- **Unpaid / ghost claims**: Buyers claim items but disappear without paying, leaving inventory blocked while other buyers were waiting.

---

## 💡 The Solution

**ClaimRoom** replaces spreadsheets and chat chaos with a dedicated, lightweight real-time sales room:
1. **Seller** creates a live room, adds products, and shares the 5-character join code (e.g. `K9X2P`), direct link (`/?code=K9X2P`), or 1-tap **Show QR** code for audience members to scan from desktop or live streams.
2. **Buyers** join live, watch products update instantly, and tap **CLAIM NOW**.
3. **Atomic Double-Claim Prevention**: Serverpod handles each claim inside a PostgreSQL database transaction with `LockMode.forUpdate`. Claims run inside a database transaction with a row lock, so only one buyer can win an item. Even if multiple buyers tap at the exact same millisecond, row-level database locking guarantees exactly one claim succeeds.
4. **Two-Layer Hold Timer & Auto-Release**: Winning claims get a **60-second hold**. Hold expiry has two layers: a Serverpod **Future Call** when enabled, plus a server-side sweep on reads (`listItems`, `getOrderSheet`, `claimItem`), so it also works where future calls are disabled (e.g. Serverpod Cloud Starter). Expired holds can also be immediately claimed by any buyer.
5. **Waitlist with Auto-Handover**: When an item is held by another buyer, any attendee can tap **Join waitlist** (only held items can be waitlisted; up to 10 entries per item). If a hold ends without a sale (expired, buyer released, or seller released), the earliest waitlisted buyer automatically becomes the new holder with a fresh 60-second hold and in-app banner ("🎉 It's your turn!"). Buyers with 3 active holds are skipped and kept in queue.
6. **Real-Time Streaming**: Serverpod streaming endpoints push live events (`item_claimed`, `item_confirmed`, `item_released`, `item_paid`, `waitlist_updated`, `sale_ended`) to all attendees simultaneously.
7. **Mark as Paid & Ghost Buyer Resolution**: Sellers can toggle paid status per item directly in the live order sheet, tracking paid vs unpaid totals in real time.
8. **Order Sheet & Multi-Format Export**: When the sale ends, the seller gets an aggregated order sheet grouped by buyer with 1-tap **Copy WhatsApp Summary** and **Copy as CSV** buttons.

## 🛠️ How Serverpod 4 is Used

| Feature | Implementation | Why It Matters |
|---|---|---|
| **Database Transactions** | `session.db.transaction((t) => ...)` with `LockMode.forUpdate` | Guarantees atomic claims; claims run inside a database transaction with a row lock, so only one buyer can win an item |
| **Waitlist & Auto-Handover** | Transactional queue handover + `WaitlistEntry` table | Automatically passes released or expired holds to the next buyer in line in the same row-locked transaction |
| **Two-Layer Hold Expiry** | `HoldExpiryFutureCall` + transactional read sweeps | Scheduled 60s auto-expiry when future calls are enabled, plus locked read-sweeps on `listItems`, `getOrderSheet`, and `claimItem` so hold expiry works even when future calls are disabled |
| **Streaming Endpoints** | `client.room.streamRoom(roomId)` via `session.messages.createStream(...)` | Real-time WebSocket event bus pushing instant state updates to all buyers & seller |
| **Shared Client** | `claimroom_client` generated by Serverpod | Type-safe shared models and endpoints between backend and Flutter frontend |
| **Embedded Database** | Serverpod embedded PostgreSQL (`config/development.yaml` & `config/test.yaml`) | Instant local setup with embedded PostgreSQL managed directly by Serverpod |
| **Serverpod Cloud** | `serverpod cloud launch` with a managed Postgres database | Server, database and the Flutter web app are deployed together from one command |
| **Protected Endpoints** | `sellerKey` validation on mutation & order endpoints | Prevents unauthorized buyers from tampering with inventory or accessing order data |

## 🚀 Getting Started

### Prerequisites
- [Flutter SDK](https://flutter.dev) (v3.44+)
- [Dart SDK](https://dart.dev) (v3.12.2+)
- [Serverpod CLI](https://serverpod.dev):
  ```bash
  dart install serverpod_cli
  ```
  *(Note: On Windows, add the Dart install `bin` folder and the Flutter `bin` folder to your `PATH` environment variable. Building Flutter plugins on Windows also needs Developer Mode turned on.)*

### Running the App Locally

1. **Clone the repository:**
   ```bash
   git clone https://github.com/MKAVINRAJ30/claimroom.git
   cd claimroom
   ```

2. **Start the Serverpod Server & Web App:**
   ```bash
   serverpod start
   ```
   *This boots the Serverpod API server (port 8080), Insights server (port 8081), applies database migrations to the embedded PostgreSQL instance, and launches the Flutter application in Chrome.*

3. **Running the Flutter App Separately (Desktop/Mobile/Web):**
   ```bash
   cd claimroom_flutter
   flutter run -d chrome
   ```

## ☁️ Deployment (Serverpod Cloud)

ClaimRoom is deployed to Serverpod Cloud (project name `claimroom`).

To deploy your own copy:
1. Install the Serverpod CLI and log in: `serverpod cloud auth login`
2. Create a project in the [Serverpod Cloud console](https://console.serverpod.dev) with the database enabled.
3. From `claimroom_server`, run:
   ```bash
   serverpod cloud launch
   ```
   This runs `serverpod generate`, builds the Flutter web app into the server's `web/app` folder, uploads, and rolls out the server.
4. The Flutter app finds the server using, in order:
   - the compile-time define `--dart-define=SERVER_URL=<your cloud API URL>`
   - `apiUrl` in `claimroom_flutter/assets/config.json`
   - `http://localhost:8080` as the local default

## 📱 How to Demo the Flow (2-Minute Demo Script)

1. **Open the app** at https://claimroom.serverpod.space on two devices or two browser windows (Window A = Seller, Window B = Buyer).
2. **Start a Live Sale**:
   - In Window A, under **"I'm a Seller"**, create a room ("Friday Thrift Drop").
   - Click **"Seed 4 Demo Items"** in the seller dashboard. Notice the 5-character room code (e.g. `K9X2P`) and your **Seller Secret Key**.
3. **Shareable Join Link & QR Code**:
   - Click **"Show QR"** on the seller dashboard to pop up a large QR code and room code for mobile attendees to scan. Or click **"Copy Join Link"** and open the URL in Window B (join code pre-filled automatically).
4. **Join as Buyer**:
   - In Window B, type your name (for example `Priya`) and join.
5. **Demonstrate Atomic Claim**:
   - Tap **"CLAIM NOW"** on an available item.
   - Notice the instant real-time update in both windows:
     - Seller sees: `HELD BY PRIYA` with live countdown timer, early release option, and waitlist badge.
     - Buyer sees: `HELD FOR YOU (0:59)` with "CONFIRM CLAIM" and "RELEASE" buttons.
     - Timer turns red when under 10 seconds.
6. **Demonstrate Waitlist & Auto-Handover**:
   - Open a third window (Window C) as buyer `Rahul`.
   - On the item held by Priya, tap **"Join waitlist"**. Rahul sees `"You are #1 in line"`, and the seller sees `"1 waiting"`.
   - In Window B, tap **"RELEASE"** (or let the 60s hold expire).
   - Instantly, Rahul's screen updates with a banner: `"🎉 It's your turn! You have 60 seconds to confirm"`, and a fresh 60-second hold timer starts for Rahul.
7. **Confirm Claim**:
   - Click **"CONFIRM CLAIM"**. Status instantly shifts to **SOLD**.
8. **End Sale & Order Sheet**:
   - In Window A, tap **"End Live Sale"**. Holds and waitlists are cleaned up and the room navigates to the order sheet.
   - In Window B & C, buyers see a **"Sale Ended"** summary card listing their confirmed purchases.
   - In Window A, toggle **PAID** on the buyer's item.
   - Click **"Copy as CSV"** or **"Copy WhatsApp Summary"**.

## 🛡️ Safety & Trust

- **No Payment Processing**: ClaimRoom does not process payments or verify physical products. Off-platform settlement (e.g. UPI, cash on delivery) is handled directly between buyer and seller.
- **Privacy First**: Buyer phone numbers and email contacts are visible to the seller only (via the authenticated order sheet) and are strictly sanitized from public room streams and buyer payloads.
- **Reporting Mechanism**: Buyers can tap "Report this room" anytime to submit concerns regarding suspicious rooms directly to the server.

## ⚠️ Known Limitations

In accordance with hackathon guidelines, scope was kept focused on the core live sale problem:
- **No User Accounts**: ClaimRoom uses session tokens and typed names to remove onboarding friction during quick livestream sales.
- **Buyer Identity**: Buyers are identified per session by a secure random 24-character session token stored locally, preventing other buyers with identical names from tampering with holds.
- **Seller Key**: Sellers are authenticated using a 16-character secret key generated on room creation.
- **Payments & Authenticity**: Payments and item authenticity are out of scope and not verified by ClaimRoom.
- **Claim Limit Concurrency**: The 3-hold limit per buyer token is checked within the item-level row-lock transaction.
- **Future Calls on Starter**: Serverpod Cloud Starter has future calls disabled, so hold expiry relies on the read-sweep layer in the live deployment.
